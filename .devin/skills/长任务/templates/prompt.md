## §1 核心循环

每次迭代严格执行以下步骤（不可跳过、不可合并）：

1. **读取本文件**（prompt.md）— 理解规则
2. **读取 PRD.md** — 找到 `⚡ 当前阶段`，定位下一个 ❌ 任务
3. **读取 progress.txt** — 确认已完成的工作，避免重复
4. **读取 friction-log.md** — 了解前人踩过的坑
5. **选择下一个未完成任务** — PRD 中第一个 ❌
   - **模式 B 额外步骤：** 检查该任务的 `依赖` 字段，确认前序任务已完成
6. **执行任务**
   - **模式 A：** 按本文件 §5 的标准步骤执行
   - **模式 B：** 按 PRD.md 中该任务的 `步骤` 字段执行，同时遵守本文件 §5 的通用规范
7. **运行对抗性自我审查** — 按 §1.1 的检查表
8. **提交代码**（如适用）— `git add . && git commit -m "task X.Y: [描述]"`
9. **追加 progress.txt** — 写入完成记录
10. **更新 PRD.md** — 翻转 ❌→✅，更新 ⚡ 指针指向下一个任务
11. **更新 friction-log.md** — 如遇到新问题则追加

### ⚠️ 硬性规则

- **每次迭代最多完成 [1] 个任务**（小任务可调整为 2-3）
- 如果任务无法完成（缺少依赖/文件不存在），记录为摩擦并跳过
- 绝不创建假文件或占位符
- 仅对本次修改的文件运行验证，不要全项目验证

## §1.1 对抗性自我审查

任务完成后，切换为"敌对审查者"角色，逐项检查：

| #   | 检查项                                   | 通过？ |
| --- | ---------------------------------------- | ------ |
| 1   | 有无硬编码文本？（应使用常量/i18n/配置） |        |
| 2   | 有无重复封装？（应复用已有组件/函数）    |        |
| 3   | 导入路径是否正确？                       |        |
| 4   | 有无未使用的导入？                       |        |
| 5   | 类型定义是否完整？（无 any）             |        |
| 6   | 命名是否符合项目规范？                   |        |
| 7   | 有无拼写错误？                           |        |
| 8   | 错误处理是否完备？                       |        |
| 9   | 是否符合目标架构模式？（§0）             |        |
| 10  | 有无遗漏的边界情况？                     |        |
| 11  | 文件位置是否正确？（§0 目录结构）        |        |
| 12  | [项目特定检查项]                         |        |

**如有违规 → 修复 → 重新检查（最多 3 轮）**
**第 3 轮仍有违规 → 记录到 friction-log.md，说明原因**

### 模式 B：通用质量门

以下规范适用于所有任务，无论任务内容如何：

**代码质量：**
- [ ] TypeScript 严格模式无错误
- [ ] 无 any 类型（确实需要时用 unknown + 类型守卫）
- [ ] 错误处理完备（try-catch + 有意义的错误信息）
- [ ] 关键路径有注释

**测试要求：**
- [ ] 核心逻辑有单元测试
- [ ] 边界情况有覆盖
- [ ] 测试命名清晰（should_XX_when_YY）

**提交规范：**
- 每个任务一个独立 commit
- 格式: `task [阶段].[编号]: [简短描述]`
- 不要 squash，不要 amend

**遇到阻塞时：**
- 依赖未完成 → 检查 progress.txt，确认依赖任务已 ✅，否则跳过
- 缺少外部依赖 → 记录到 friction-log 并跳过，标注 ⏭️
- 任务描述不清晰 → 做最合理的推断，标注 ⚠️，记录到 friction-log

## §8 摩擦日志协议

### 何时写入（必须记录）
- API / 库的行为与文档不一致
- 导出/导入路径发现错误
- 组件接口与 §3 定义不符
- 任何需要后续代理注意的"坑"
- 模式 B：任务描述不清晰的地方
- 模式 B：发现的跨任务隐性依赖

### 写入格式
```markdown
### [日期] [简短标题]
- **问题**: 具体描述
- **解决**: 你是如何绕过的
- **影响范围**: 哪些后续任务/文件会受影响
- **任务**: 在哪个任务中发现的
```

### 何时读取（必须阅读）
- 每次迭代开始时（步骤 4）
- 遇到意外错误时（可能前人已记录解决方案）
