# 架构变更前置验证

> 触发条件：当需要修改多个文件的架构、改变组件间关系、或引入新的设计模式时

## 1. 理解现有架构（必须）

在提出任何设计方案之前：

```
□ 阅读相关的 spec/*.md 和 docs/*.md 文档
□ 查看涉及组件的代码，理解当前实现
□ 深入理解用户的实际需求
□ 阅读 .agent\workflows\架构与设计规范.md   .agent\memory.md
□ 绘制当前架构图（组件关系、数据流、层级）
□ 记录关键设计决策点（如：谁负责 transform？谁管理生命周期？）
```

**关键问题清单**：
- 这个组件在整个系统中的角色是什么？
- 它与父组件、子组件的关系是什么？
- 现有的生命周期是如何管理的？
- 有哪些隐式的依赖或假设？

## 2. 网络验证（必须）

验证时要问**正确的问题**：

```
□ 验证"这种做法是否是最佳实践"（适配性）
□ 验证"这种改动会影响什么"（影响范围）
□ 不只验证"这个API能不能用"（可行性）
```

**搜索关键词示例**：
- "xxx 最佳实践"
- "xxx vs yyy 对比"
- "xxx 常见问题"
- "xxx 与 zzz 集成"

## 3. 影响分析（必须）

在动手之前，明确回答：

```
□ 哪些文件会被修改？
□ 改动后组件的返回值、接口、行为有变化吗？
□ 父组件对子组件有什么假设？改动后还成立吗？
□ 是否有隐式的依赖关系被打破？
```

**踩坑案例**：
- PixiClipLayer 假设子组件返回 JSX 元素
- 改造后子组件返回 null → 假设不成立 → 定位失效

```

## 4. 回退方案（必须）

```
□ 记录当前的 git commit
□ 拆解任务需求, 根据任务量合理创建多个阶段待完成任务到文档
□ 在文档上标明,每完成一个阶段功能, 就即使提交Git,并且回填文档任务状态, 直到全部任务完成
```

# 避坑检查清单

在设计阶段，对照以下问题案例：

| # | 检查项 | 本次案例 |
|---|--------|----------|
| 1 | 是否理解了现有架构的每个层级的职责？ | ❌ 没有分析 PixiClipLayer |
| 2 | 网络验证是否包含"适配性"和"影响范围"？ | ❌ 只验证了技术可行性 |
| 3 | 改动后，上游组件的假设还成立吗？ | ❌ PixiClipLayer 假设被打破 |
