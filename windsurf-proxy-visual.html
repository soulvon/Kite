1. 双端口路由拓扑

PORT 3000 🔓 hybrid-server (HTTP/1.1)
@/orderProject/windsurf-proxy/src/hybrid-server.js
深度拦截 HTTP/1.1 代理流量。针对核心域名 server.self-serve.windsurf.com 执行本地 TLS 终结（利用 mkcert 根证书自签），捕获聊天接口（GetChatMessage），而非核心流量（如遥测、登录）则一律盲传放行。
PORT 3001 ⚡ inference-proxy (HTTP/2)
@/orderProject/windsurf-proxy/src/inference-proxy.js
承接内嵌 AI 编辑器的流式 HTTP/2 通信。由于客户端直连，此模块使用虚拟 HTTP/1.1 适配器桥接完成转换，拦截行内编辑触发的 GetChatMessage 消息，而代码补全流量则放行回 Codeium。

2. Connect-RPC 协议封装规范

CONNECT-RPC OVER GRPC FRAME MODEL
Flags (1 Byte)
0x01: Gzip / 0x03: EOS
Length (4 Bytes, BE)

Serialized Payload (N Bytes)
Gzipped Protobuf Data
• 上行解包：接收数据流后，截取前 5 字节。如果是压缩包（Flags = 1），通过 zlib.gunzipSync 还原为原始二进制流。
• 下行封包：通过 zlib.gzipSync 压缩上行模型输出，装配 5 字节头部写入 socket 连接，并在流末尾追加 endOfStreamEnvelope 结束信号帧。

3. 消息逆向与严格角色并组

⚠️ 契约冲突防御逻辑：
Windsurf 在协同场景下可能发出多段连续的 TOOL (Source: 4) 返回帧。直接转换为模型上行报文会导致出现连续的多个 user 角色消息块。由于 Anthropic 契约强制要求角色必须严格交替，代理通过 mergeConsecutiveMessages 将同角色的相邻消息无缝归并到统一的内容数组中，从而安全避开云端 API 的报错规则。
上行协议解析与归并逻辑：
  • 1 (USER) ──► 转换为 LLM 的 user 角色
  • 2 (SYSTEM) / 3 (UNKNOWN) ──► 转换为 assistant 角色（提取字段 11 作为思维链输入）
  • 4 (TOOL) ──► 封装为 tool_result 并强行归并入上一个 user 的 content 数组
  • 5 (SYSTEM_PROMPT) ──► 作为动态环境变量，串联在 Top-level 静态 System Prompt 尾部
