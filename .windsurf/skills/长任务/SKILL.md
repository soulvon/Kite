# 长任务自主循环（Autonomous Task Loop）

## 概述

当你面对一个**需要多次迭代才能完成的大型任务**，手动逐个处理效率极低。本技能提供一套**三文件协调系统**，让无状态代理能跨会话持续推进任务。

**核心理念：** 每次迭代启动时没有任何记忆——它只知道文件里有什么。正是这种限制让文档设计变得重要。

**宣告：** "我正在使用「长任务」技能来设置自主循环任务。"

---

## 两种任务模式

本技能支持两种不同类型的大任务：

### 🔄 模式 A：批量重复型

**特征：** 同一套步骤 × N 个目标

| 场景     | 示例                           |
| -------- | ------------------------------ |
| 批量迁移 | 80 个组件从 Class 迁移到 Hooks |
| 逐页审计 | 350 个页面统一修复架构问题     |
| 模式对齐 | 所有 API 路由统一错误处理      |
| 代码规范 | 全项目文件统一命名/导入规范    |

**prompt.md 侧重：** 标准化步骤——同一套流程反复执行
**PRD.md 格式：** 简洁清单——每个任务一行，步骤看 prompt.md

```markdown
- ❌ 任务 2.15：迁移 UserProfile 组件     ← 步骤见 prompt.md §5
- ❌ 任务 2.16：迁移 Settings 组件         ← 步骤见 prompt.md §5
```

---

### 🏗️ 模式 B：项目构建型

**特征：** 每个任务步骤不同，但都是同一个大目标的子任务

| 场景     | 示例                                                       |
| -------- | ---------------------------------------------------------- |
| 从零搭建 | 搭建完整的 SaaS 后端（数据库→API→认证→权限→...）           |
| 大型重构 | 前端架构从 Redux 迁移到 Zustand（规划→核心→页面→测试→...） |
| 复杂功能 | 实现完整视频翻译管线（ASR→翻译→TTS→合成→UI→...）           |
| 系统集成 | 对接 10 个第三方 API（支付→邮件→SMS→存储→...）             |

**prompt.md 侧重：** 通用规范和质量门——每个任务做什么不同，但怎么做遵循同一套标准
**PRD.md 格式：** 详细描述——每个任务都有独立的执行说明和验收标准

```markdown
- ❌ 任务 2.1：实现用户注册 API
  - 路由: POST /api/auth/register
  - 参数: email, password, name
  - 加密: bcrypt, saltRounds=12
  - 响应: { user, token }
  - 验收: 单元测试通过 + 手动 curl 测试
```

---

### 模式选择指南

```
你的任务中，每个子任务的步骤是否基本相同？
                  │
          ┌───────┴───────┐
          │               │
        是的             不是
     (80%+ 相同)     (每个都不同)
          │               │
     模式 A：批量型    模式 B：构建型
     步骤写 prompt     步骤写 PRD
     PRD 只列清单      PRD 写详细说明
```

## 核心架构：三文件协调系统

```
┌─────────────────────────────────────────────────┐
│              迭代开始（全新上下文）                  │
│                                                   │
│   1. 读取 prompt.md    → "以下是规则和步骤"        │
│   2. 读取 PRD.md       → "这是范围 + 下一个任务"   │
│   3. 读取 progress.txt → "已经完成了什么"          │
│   4. 读取 friction-log.md → "前人踩过的坑"        │
│   5. 选择下一个未完成任务（PRD 中第一个 ❌）        │
│   6. 执行任务                                     │
│   7. 对抗性自我审查（检查表）                       │
│   8. 更新 progress.txt（追加完成记录）             │
│   9. 更新 PRD.md（❌ → ✅，更新下一个任务指针）      │
│  10. 更新 friction-log.md（如有新问题）            │
│                                                   │
│              迭代结束 → 循环重启                    │
└─────────────────────────────────────────────────┘
```

| 文件              | 职责                                                 | 类比       |
| ----------------- | ---------------------------------------------------- | ---------- |
| `prompt.md`       | 无状态说明书 — 规则、步骤（模式A）或规范（模式B）    | 员工手册   |
| `PRD.md`          | 状态机 + 任务列表 — 当前阶段指针 + 任务详情（模式B） | Jira 看板  |
| `progress.txt`    | 仅追加完成日志 — 每个代理的收据                      | 签到表     |
| `friction-log.md` | 摩擦日志 — 制度记忆系统                              | 经验知识库 |

## 第一步：分析任务并规划

在创建文件之前，先回答以下问题：

1. **模式选择：** 是批量重复型（A）还是项目构建型（B）？
2. **任务总量：** 列出所有需要处理的文件/模块/功能点
3. **执行步骤：** 
   - 模式 A → 定义标准化的统一执行流程
   - 模式 B → 为每个任务定义独立的执行说明
4. **验证标准：** 定义质量门（类型检查、测试、代码规范）
5. **已知的坑：** 提前记录到 friction-log
6. **阶段划分：** 按依赖关系分阶段，阶段内任务尽量独立
7. **每次迭代的任务量：**
   - 默认每次 1 个任务（原子性最强）
   - 如果任务很小（< 5 分钟），可以设为每次 2-3 个

## 第二步：创建 prompt.md（说明书）

模板见 [templates/prompt.md](templates/prompt.md)。

### 两种模式下的 prompt.md 侧重点不同

#### 模式 A（批量型）的 prompt.md：~200-500 行

重点是**标准化执行步骤**，因为每个任务都走同一套流程。

```markdown
## §5 标准任务执行步骤（每个任务都走这套流程）

1. 读取目标文件，理解当前状态
2. 检查是否使用旧模式（Class 组件 / BEM 命名 / ...）
3. 按新模式重写
4. 运行类型检查：`npx tsc --noEmit [目标文件]`
5. 如果失败 → 修复 → 重试（最多 3 次）
6. 如果文件不存在 → 记录为摩擦并跳过
```

#### 模式 B（构建型）的 prompt.md：~100-300 行

重点是**通用规范和质量门**，具体步骤在 PRD 里。

```markdown
## §5 通用执行规范

### 代码质量门（每个任务都必须过）
- [ ] TypeScript 严格模式无错误
- [ ] 无 any 类型
- [ ] 错误处理完备（try-catch + 用户提示）
- [ ] 关键路径有单元测试
- [ ] 符合项目目录结构规范

### 提交规范
- 每个任务一个独立 commit
- 格式: `task [阶段].[编号]: [描述]`

### 遇到阻塞时
- 如果依赖前序任务的产出 → 检查 progress.txt 确认已完成
- 如果缺少外部依赖 → 记录到 friction-log 并跳过
- 如果任务描述不清晰 → 记录为摩擦，做最合理的推断，标注 ⚠️
```

### 两种模式都必须包含的章节

#### §0 — 架构北极星
项目的设计理念和约束。让每个代理理解"为什么"。

#### §1 — 核心循环
代理每次迭代必须遵循的精确步骤。

```markdown
## §1 核心循环

每次迭代严格执行以下步骤：
1. 读取本文件（prompt.md）
2. 读取 PRD.md → 找到"⚡ 当前阶段"
3. 读取 progress.txt → 确认已完成的工作
4. 读取 friction-log.md → 了解前人踩过的坑
5. 选择下一个 ❌ 任务
6. 执行任务
   - 模式 A：按本文件 §5 的标准步骤执行
   - 模式 B：按 PRD.md 中该任务的说明执行
7. 运行对抗性自我审查（详见 §1.1）
8. 提交代码（如适用）
9. 追加 progress.txt
10. 更新 PRD.md（翻转 ❌→✅，更新⚡指针）
11. 更新 friction-log.md（如遇到新问题）

⚠️ 硬性规则：每次迭代最多完成 [N] 个任务！
```

#### §1.1 — 对抗性自我审查
任务完成后，代理以"敌对审查者"身份重审自己的工作。最多循环 3 次直到违规归零。

```markdown
## §1.1 对抗性自我审查检查表

完成任务后，以审查者身份检查以下项目：

1. [ ] 有无硬编码文本？（应使用常量/配置）
2. [ ] 有无重复封装？（应复用已有组件/函数）
3. [ ] 导入路径是否正确？
4. [ ] 有无未使用的导入？
5. [ ] 类型定义是否完整？（无 any/unknown）
6. [ ] 命名是否符合项目规范？
7. [ ] 有无拼写错误？
8. [ ] 错误处理是否完备？
9. [ ] 是否符合目标模式/架构？
10. [ ] 有无遗漏的边界情况？
11. [ ] 文件是否在正确的目录位置？
12. [ ] [项目特定检查项]

如有违规 → 修复后重新检查，最多循环 3 次。
如果第 3 次仍有违规 → 记录到 friction-log.md 并继续。
```

#### §3 — 锚定类型/接口（可选但推荐）
将核心组件的接口定义直接粘贴到 prompt 中，避免代理每次都读源文件。

#### §8 — 摩擦日志协议
定义何时写入、何时读取摩擦日志。

#### §9 — 速查表（可选）
"如果你的数据形如 X，使用组件 Y"。防止代理造轮子。

## 第三步：创建 PRD.md（状态机）

模板见 [templates/PRD.md](templates/PRD.md)。

### 最关键的部分：⚡ 当前阶段指针

```markdown
## ⚡ 当前阶段 — 先读此

> **第一阶段 100% 完成（50/50）。** 不要扫描第一阶段。
>
> **活跃阶段：第二阶段 — 组件迁移**
> **下一个任务：任务 2.15 — 迁移 UserProfile 组件**
> **说明：详见 prompt.md §5（模式A）/ 见下方任务详情（模式B）**
```

**没有这个指针，代理会浪费大量 token 扫描已完成的任务。**

### 模式 A 的任务清单（简洁版）

```markdown
## 第二阶段：组件迁移

- ✅ 任务 2.1：迁移 Header 组件
- ✅ 任务 2.2：迁移 Footer 组件
- ❌ 任务 2.15：迁移 UserProfile 组件   ← 当前
- ❌ 任务 2.16：迁移 Settings 组件
```

### 模式 B 的任务清单（详细版）

```markdown
## 第二阶段：核心 API 实现

- ✅ 任务 2.1：实现用户注册 API
- ✅ 任务 2.2：实现用户登录 API

- ❌ 任务 2.3：实现 JWT Token 刷新   ← 当前
  **目标**: 实现 access token 过期后的自动刷新机制
  **文件**: `src/api/auth/refresh.ts`, `src/middleware/auth.ts`
  **步骤**:
  1. 创建 POST /api/auth/refresh 端点
  2. 验证 refresh token（从 httpOnly cookie 读取）
  3. 签发新 access token（15 分钟有效期）
  4. 如果 refresh token 过期 → 返回 401，要求重新登录
  **验收标准**:
  - [ ] 单元测试：有效/过期/篡改 token 三种情况
  - [ ] refresh token 轮转（每次刷新同时更新 refresh token）
  **依赖**: 任务 2.1（User 模型）、任务 2.2（JWT 工具函数）

- ❌ 任务 2.4：实现用户资料 CRUD
  **目标**: 用户个人资料的增删改查
  **文件**: `src/api/users/profile.ts`
  **步骤**:
  1. GET /api/users/me — 获取当前用户资料
  2. PATCH /api/users/me — 更新资料（name, avatar, bio）
  3. 头像上传走 multipart/form-data，存到 S3
  **验收标准**:
  - [ ] 接口测试通过
  - [ ] 文件上传大小限制 5MB
```

### 阶段规划

```markdown
## 阶段概览

| 阶段 | 描述         | 任务数 | 完成 | 状态     |
| ---- | ------------ | ------ | ---- | -------- |
| 1    | 基础设施准备 | 10     | 10   | ✅ 完成   |
| 2    | 核心 API     | 15     | 2    | 🔄 进行中 |
| 3    | 前端页面     | 20     | 0    | ⏳ 等待   |
| 4    | 集成测试     | 8      | 0    | ⏳ 等待   |
| 5    | 部署上线     | 5      | 0    | ⏳ 等待   |
```

## 第五步：创建 friction-log.md（摩擦日志）

模板见 [templates/friction-log.md](templates/friction-log.md)。

**工作机制：**
```
迭代 N 遇到摩擦 → 记录到 friction-log.md
                      ↓
迭代 N+1 读取日志 → 避免同样的坑
                      ↓
迭代 N+1 发现新摩擦 → 继续记录
                      ↓
系统持续改进
```

**模式 B 特别提醒：** 不重复的任务之间也会有共性的坑！比如：
- 同一个 ORM 的 API 陷阱（在任务 2.1 发现，任务 2.4 也会踩）
- 项目配置的隐含约束（发现 S3 需要特定 IAM 权限）
- 代码生成器/脚手架的 bug
- 第三方库版本不兼容

这些"跨任务"的经验正是 friction-log 在模式 B 下的核心价值。

## 关键设计决策

### 1. ⚡ 当前阶段指针
**最重要的设计。** 防止代理在已完成的工作上浪费上下文窗口。每次更新时同步更新指针。

### 2. 每次迭代的任务量控制
- **默认 1 个任务/迭代** — 原子性最强，失败不扩散
- **小任务可合并 2-3 个** — 但必须在 prompt.md 中明确声明
- **绝不贪多** — 任务 3 的错误不应破坏任务 1-2

### 3. 对抗性自我审查
检查表循环捕捉类型检查遗漏的违规。这是"它能编译"和"它是正确的"的区别。

### 4. 摩擦日志作为制度记忆
每次迭代都是遗忘的，friction-log.md 是跨迭代学习的唯一途径。
- **模式 A：** 前人踩了坑，后人不再踩（同类错误传递）
- **模式 B：** 跨任务的隐性知识积累（不同任务可能共享相同的坑）

### 5. 范围验证
代理只对自己修改的部分进行验证，而非整个项目。

### 6. 锚定接口
核心类型定义直接写入 prompt.md，消除"属性名猜错"这一整类错误。

### 7. 依赖声明（模式 B 专属）
非重复任务之间可能有前后依赖。PRD.md 中用 `**依赖**: 任务 X.Y` 声明，代理在执行前检查依赖是否已完成。

## 如何用 AG 生成这些文件

你不需要手动写数百行的 prompt.md。

### 准备输入材料

| 材料                                 | 用途                 | 必需？ |
| ------------------------------------ | -------------------- | ------ |
| 项目规则文件（GEMINI.md）            | 写入 prompt.md §0    | ✅      |
| 架构文档 / README                    | 理解项目结构         | ✅      |
| 文件列表（模式A）或功能规格（模式B） | 生成 PRD.md 任务清单 | ✅      |
| 核心 TypeScript 接口                 | 写入 prompt.md §3    | 推荐   |
| 已知问题 / 注意事项                  | 初始化 friction-log  | 可选   |

### 让 AG 生成

**模式 A 的提示词：**
```
/长任务

我需要对 [描述范围] 进行批量 [操作类型]，共 [N] 个文件。

每个文件的处理步骤相同：
1. [步骤 1]
2. [步骤 2]
3. [步骤 3]

文件列表：[粘贴或指定目录]
项目规范：[粘贴或指定文件]
```

**模式 B 的提示词：**
```
/长任务

我需要从零搭建 [描述系统]，包含以下功能模块：
1. [模块 1 + 简述]
2. [模块 2 + 简述]
3. [模块 N + 简述]

每个模块的步骤各不相同，请为每个任务生成详细的执行说明。
技术栈：[列出技术栈]
项目规范：[粘贴或指定文件]
```

## 与其他技能的关系

| 技能                             | 关系                   | 什么时候用那个                            |
| -------------------------------- | ---------------------- | ----------------------------------------- |
| `planning-with-files`            | 长任务是其超集         | 5-20 步的简单任务用 planning-with-files   |
| `executing-plans`                | 单次执行 vs 循环执行   | 一个会话能完成的用 executing-plans        |
| `writing-plans`                  | 编写计划               | 先用 writing-plans 想清楚，再用长任务执行 |
| `verification-before-completion` | 对抗性自我审查的基础版 | 简单任务用 verification                   |
| `code-review-lite`               | 补充审查               | 长任务完成后做一次总体审查                |

### 选择指南

```
任务多大？
  │
  ├─ 1 个会话能搞定 → executing-plans / planning-with-files
  │
  └─ 需要多个会话 → 长任务
                       │
                       ├─ 每个任务步骤相同 → 模式 A
                       └─ 每个任务步骤不同 → 模式 B
```

## 预期效果

### 模式 A（批量型）参考数据
- **368 个子页面迁移** 全自主完成
- 每次迭代耗时 ~2-4 分钟
- 对抗性审查平均每任务捕获 3-7 次违规
- 零人工干预完成整个阶段

### 模式 B（构建型）参考数据
- 适合 10-100+ 个不同子任务的项目
- 每次迭代耗时 ~5-15 分钟（任务更复杂）
- friction-log 在 ~10 次迭代后显著减少新坑
- 建议每 10 个任务人工抽检一次

## 反模式

| ❌ 不要                 | ✅ 应该                                 |
| ---------------------- | -------------------------------------- |
| 一次迭代处理过多任务   | 控制在 1-3 个任务/迭代                 |
| 跳过自我审查           | 每次都运行检查表                       |
| 手动维护任务状态       | 用 ⚡ 指针自动定位                      |
| 忽略遇到的问题         | 全部记录到 friction-log                |
| 在 prompt 中写模糊指令 | 提供精确步骤（A）或详细说明（B）       |
| 让代理全项目类型检查   | 仅检查本次修改的范围                   |
